# Hierarchical Layout Skill — Implementation Plan

Plan for turning [HIERARCHICAL_TREE_SPEC.md](../../hierarchical/HIERARCHICAL_TREE_SPEC.md) into an Anthropic-style **Skill** that the Claude agent invoked by **Octo** uses to generate `Page` artifacts from a prompt.

This is a production component, not a human-facing help doc. The skill is the agent's playbook — loaded into every generation run, with no human in the loop between prompt and emitted artifact.

> **Status**: all v0 component prerequisites are complete and committed.
>
> - Layout primitives — `0a308c816` (Row, Column, Stack, Grid, Container, Cluster, SplitView in `packages/ui/src/components/layout/`).
> - Static-page-atom primitives — `c564f2704` (Heading + Text in `packages/ui/src/components/typography/`; Divider, Link, Icon in `packages/ui/src/components/{divider,link,icon}/`).
> - Authored-structure interactive atoms — already shipped in `@genuin/ui` (Accordion, Tabs, Collapsible).
>
> **Initial consumers**: publishers — iHeartRadio, US Weekly, Sacramento Bee (McClatchy). The `pageTypeHint` taxonomy and archetype expectations are tuned to news / entertainment / media-property publishing, not e-commerce or product marketing.
>
> All v0 decisions are locked: Octo integration shape (skill loads from `.claude/skills/hierarchical-tree/SKILL.md` in the sandbox; Figma MCP is available to the agent at generation time), primitive scope (layout + static-page atoms + authored-structure interactive atoms), output format (TypeScript), `pageTypeHint` taxonomy (`article | recap | topic-hub | gallery | section`, free-string fallback), test harness location (new page in `apps/webapp/`), validator location (`scripts/`), and v0 quality bar (human review for first 2 weeks).
>
> **Golden-artifact strategy: bootstrap-then-promote.** No hand-authored Page artifacts ship in v0. The skill produces outputs; outputs that pass validator + human review during the first-2-weeks review window get promoted into `apps/webapp/src/content/page-artifacts/golden/` as regression fixtures and as in-context examples for later skill iterations. Visual reference during human review is the Figma file (see spec §6) — agents can fetch design context directly via Figma MCP.
>
> **All v0 open items resolved.** Chunks 2 onward (Zod schema → validator → SKILL.md → smoke test → promotion pipeline) can proceed without external blockers.
>
> **Runtime walker is shipped** — `@genuin/hierarchical-tree` landed in commits `e38d708e9` (package: schema + walker + default registries + `<PageRenderer>`) and `fc90591bf` (smoke-test page at `/hierarchical/preview` in `apps/webapp/`). The package owns the `Page` Zod schema + types + walker + default renderers + rule-check space, all consumable from `@genuin/hierarchical-tree/schema` and the package root. ## What the skill must contain

The skill is self-contained. The agent has the skill + the prompt; nothing else (unless we explicitly pipe in extra context like the `uiVariant` manifest as input).

| Section | Content | Why |
|---|---|---|
| **Frontmatter** | `name: hierarchical-tree`, `description: …`, possibly `tools:` allowlist if Octo's harness honours it. | Skill identity. |
| **Inputs contract** | Exact shape: `{ prompt: string; pageTypeHint?: 'article' \| 'recap' \| 'topic-hub' \| 'gallery' \| 'section' \| string; breakpoints: number[] }`. The locked enum is publisher-tuned per Q3; free-string fallback handles anything outside the set. | Agent needs to parse its input deterministically. |
| **Output schema (literal)** | Full TypeScript types from spec §2.1–§2.3 (`Page`, `LayoutTree`, `LayoutNode`, `UiNode`, `SlotNode`, `SlotKind`) restated inline. | No "go read the spec" possible at runtime. |
| **Page archetypes** | One short template per locked `pageTypeHint`: **article** (text-centric long-form), **recap** (event recap with video anchor), **topic-hub** (entity landing — celebrity / team / show / artist), **gallery** (photo-first listicle), **section** (category / vertical landing). Each shows the canonical tree shape for that archetype at the mobile and desktop breakpoints. | Lets the agent skip from prompt → shape. |
| **Composing rules (algorithmic)** | Step-by-step procedure: (1) parse inputs; (2) for each breakpoint, run Phase 1 (anchor Content + `feed` video); (3) run Phase 2 (fold-driven interleave per spec §5.2 table); (4) apply count budgets per spec §5.6; (5) validate output; (6) emit. | Agent follows steps; humans read prose. |
| **Per-breakpoint budgets** | Spec §5.6 table restated as hard constraints. | Caps output size; flags off-pattern outputs. |
| **Fold-based placement rule** | Spec §5.3: above-fold = anchor + personalize (small high-confidence tiles); below-fold = densify for exploration (carousels, grids). | Drives Phase 2 decisions. |
| **Input-model heuristic** | Spec §5.6: mobile = swipe/tap → `feed`; desktop = hover/click → `grid` / `carousel`. | Drives placement-style picks per breakpoint. |
| **Closed UI vocabulary** | Enumerated list of the 20 valid `uiVariant` strings: 7 layout primitives (`row`, `column`, `stack`, `grid`, `container`, `cluster`, `split-view`), 10 static-page atoms (`button`, `avatar`, `chip`, `image`, `decorative-list`, `heading`, `text`, `divider`, `link`, `icon`), and 3 authored-structure interactive atoms (`accordion`, `tabs`, `collapsible`). Each entry: name, what it does, prop shape, when to use. **No composites in v0** (per spec §7); host registers composites later via `uiRenderers` if needed. **Explicit deny-list** for the runtime-only primitives (`dialog`, `popover`, `tooltip`, form controls, etc.) per spec §4.2 — the agent must never emit those. | Without this the agent invents component names or reaches for runtime-only primitives. |
| **Content body format + markdown allowlist** | The `content` Slot's `body` prop is **markdown** (rendered by the walker via `react-markdown` with a constrained allowlist — see [HIERARCHICAL_TREE_RUNTIME_WALKER_PLAN.md](HIERARCHICAL_TREE_RUNTIME_WALKER_PLAN.md) "Content body markdown allowlist"). Allowed: paragraphs, emphasis/strong, inline links, lists, blockquotes, inline code, line breaks, **H2/H3 subsection headings**, **inline figures with captions**. Disallowed: H1 (page-level — use a `heading` UI node), H4–H6, code blocks, tables, HTML passthrough, MDX/component embeds. Plus the page-level-vs-body-internal rule (spec §4.3): if removing the element would break the *flow of the prose*, it's body content; if it could stand alone as a separate section, it's a UI node. | Tells the agent what to put inside content vs in the tree, and what markdown is safe to emit. |
| **Hard rules / fail conditions** | Spec §3.7, §4.1, §2.5 "what is NOT allowed" lists, each stated as a self-check the agent performs before returning. | Self-validation pass. |
| **Worked examples** | 2–3 full prompt → `Page` artifact examples. Mix of archetypes. At least one mobile + desktop pair. | In-context learning is the strongest signal. |
| **Negative examples** | Anti-templates from spec §3.7 + Appendix B: substring-name kind inference, nav as a Slot, `style: 'single'` on a video, multiple component instances per Slot, etc. | Pre-empts known failure modes. |
| **Failure path** | What the agent does when it cannot produce a valid Page (e.g. ambiguous prompt, missing pageTypeHint, validation failure after N retries): emit a structured error rather than a partial Page. | Defines the "I can't" output shape. |

## What needs to exist alongside the skill

The skill alone is not shippable. These items are required for the generator to be usable in production.

### 1. Page artifact validator (Zod schema + rule checks)

A programmatic validator that asserts:

- **Schema validity**: matches the TypeScript types in spec §2.1–§2.3. The Zod schema lives in [`@genuin/hierarchical-tree`](HIERARCHICAL_TREE_RUNTIME_WALKER_PLAN.md) (`packages/hierarchical-tree/src/schema.ts`) as part of the runtime walker package — it's the single source of truth for the artifact contract, shared between the validator and the runtime.
- **Tree rules** from spec §2.5: Slots are leaves, no Slot inside a Slot, no global grid-placement props on UI nodes.
- **Slot rules** from spec §3.7: every Slot has a `kind`; renderers don't mount multiple instances; `style` is valid for the kind.
- **Slot-filling priority** from spec §5: Phase 1 satisfied before Phase 2 placements.
- **Budget rules** from spec §5.6: slot counts within bounds for the breakpoint.

**Where**: `scripts/validate-page-artifact.mjs` — a thin CLI wrapper that imports `pageSchema` and the rule-check helpers from `@genuin/hierarchical-tree`. The package owns the contract; the script owns the CLI ergonomics.

**How to load the artifact** (because output format is TypeScript, not JSON): use `tsx` (or `vite-node` / `jiti`) to import the artifact module at runtime and validate the exported `page` value against `pageSchema`. ~20 lines of glue around `import('…')` + `pageSchema.safeParse(mod.page)`. Avoid AST-parsing the source — runtime evaluation is simpler and gives accurate values for any computed props the generator emits.

**Used by**: (a) the agent calls the CLI before returning; (b) CI runs it on every committed `Page` artifact under `apps/webapp/src/content/page-artifacts/`; (c) the smoke-test page imports the schema directly from `@genuin/hierarchical-tree` and may call it to surface "this Page didn't pass" warnings in dev.

**Effort**: ~0.5 day for the CLI wrapper + rule-check helpers in the package (the Zod schema itself is built in chunk 1 of the runtime walker plan, not here).

| `uiVariant` string | Component | Key props | Status |

#### Excluded from v0 (per spec §4.2's runtime / interaction category)

Not in the manifest, never emitted by the agent: `dialog`, `popover`, `tooltip`, `sheet`, `dynamic-sheet`, `hover-card`, `command`, `loader`, `skeleton`, `toaster`, `table`, form controls (`input`, `select`, `checkbox`, `radio-input`, `textarea`, `switch`, `slider`, `phone-input`, `input-otp`, `label`, `form`), and `video-player` / `audio-player` (reached through the `video` Slot kind, not as UI nodes).

#### Typography primitives — done

`Heading` and `Text` were added in chunk 1b as sibling primitives in `packages/ui/src/components/typography/`, sharing a `tokens.ts` font-class map derived from the Figma master design system (node `1821:46389`). Two components instead of one: `Heading` covers Display + Headline tiers (8 size tokens, 20–100px); `Text` covers Body tier (5 size tokens, 8–16px). Matches the semantic HTML split — `Heading` for page/section titles, `Text` for paragraphs, captions, labels. Both server-component-safe, asChild via Radix Slot, `data-slot` attributes.

#### Divider / Link / Icon — done

Three static-page-atom primitives added in commit `c564f2704` (chunk 1c). Original audit identified that `@genuin/ui` lacked all three; built to fill the gap.

- **`Divider`** — horizontal/vertical separator with `role="separator"` + `aria-orientation`. Three tones (`default`/`subtle`/`strong`) mapping to the project's `secondary-*` gray scale. Horizontal-only `inset` token. `asChild` for swapping in `<hr>` when document outline demands it.
- **`Link`** — framework-agnostic anchor (no `next/link` import). Tones `default`/`subtle`/`inverted` mapping to `primary-*` action color and inverted text. Three underline modes (`always`/`hover`/`none`). `external=true` adds `target="_blank" rel="noopener noreferrer"` plus a visual `↗` indicator. Focus visibility preserved via `focus-visible:ring-2 ring-primary-400`. Consumers wrap with `<NextLink asChild>` for client routing.
- **`Icon`** — thin wrapper around `lucide-react` with a closed `IconName` enum (~25 curated icons: `arrow-*`, `chevron-*`, `check`, `x`, `plus`, `minus`, `search`, `menu`, `more-*`, `share`, `bookmark`, `heart`, `star`, `external-link`, `link`, `copy`, `play`, `pause`, `info`, `alert-circle`, `help-circle`). Size tokens `xs`/`sm`/`md`/`lg`/`xl` map to 12/14/16/20/24px. `aria-label=""` is the decorative sentinel (component drops `role="img"` and adds `aria-hidden="true"`); non-empty labels get `role="img"` + the accessible name.

54/54 tests pass across the three suites; typecheck clean.

#### Composites

**No composites in v0.** `<PageHeader>`, `<MetaPanel>`, `<LinkoutStack>` and the other composites referenced in spec §2.4's example tree don't exist yet. The agent's v0 output composes pages from primitives + atoms only, producing flatter trees than the spec example. Composites get promoted from the spec §7 "ad-hoc per page" policy after we observe what patterns the generator emits repeatedly — usage-driven, not designed up front.

#### v1 — generated manifest

After enough real generations to see which composites earn their place, switch to a generated `composites-manifest.json` built from `uiRenderers`. Triggered when the curated composite set grows beyond ~15 entries or when inline drift becomes a real source of agent error.

### 3. Golden Page artifacts — bootstrap-then-promote

**v0 ships without hand-authored golden Page artifacts.** Hand-authoring goldens upfront would require committing to archetype shapes before the generator has produced any — which means either guessing the shape (risk of wasted work when the agent disagrees) or waiting on archetype templates (blocker we'd rather not have). The strategy instead:

1. **Bootstrap (chunks 5–6 of the implementation plan)** — the skill ships with the inline `uiVariant` manifest, the algorithmic composing rules, the spec §2.4 example tree as a worked example, and a small synthetic mobile example seeded inline in the SKILL.md (~10 lines of `Page` JSON-as-TS, just enough to anchor the schema shape). No real-page goldens.
2. **Generate (chunk 7 — smoke test with Octo)** — the agent produces Page artifacts for the canonical archetype prompts (`article`, `recap`, `topic-hub`, `gallery`, `section` × mobile/desktop). The Figma references in spec §6 + the Figma MCP available to the agent (confirmed — the octo sandbox has Figma MCP installed) provide the visual target.
3. **Review (the first-2-weeks human-review window, Q7's quality bar)** — editorial / design team reviews each generated artifact against the Figma frames. Validator-pass is necessary but not sufficient; visual fidelity is the gating criterion.
4. **Promote (new chunk — promotion pipeline)** — when an output is approved, run `scripts/promote-page-artifact.mjs <generation-id>` to copy the artifact into `apps/webapp/src/content/page-artifacts/golden/<archetype>-<breakpoint>.ts` with metadata (prompt, breakpoint, approval source). Promoted artifacts then serve as (a) regression fixtures for the eval harness, (b) in-context examples for subsequent SKILL.md iterations.

**Visual reference during bootstrap**: the Figma file linked in spec §6. The agent reads frames directly via Figma MCP (`get_design_context` / `get_metadata`), so generations can be anchored to the design without us round-tripping screenshots through the SKILL.md.

**Where promoted goldens live**: `apps/webapp/src/content/page-artifacts/golden/` (co-located with the smoke-test page that loads them — locked per Decisions section). Empty in v0; populated as approvals come in.

**Risk and how we manage it**: bootstrap-then-promote means early generations have no anchored regression target. The first-2-weeks review window absorbs this — every output is human-reviewed, so a bad generation can't ship. As the corpus grows the eval harness gains real diff-targets and the human-review burden drops naturally.

### 4. Eval harness

A test runner that:
- Loads the skill (as a prompt or via the Octo harness).
- Sends N canonical prompts.
- Captures each output and runs it through the validator.
- Reports pass-rate, fail reasons, and — once the golden corpus exists — diffs against golden expected output.

**v0 limitation**: with no goldens at launch (per the bootstrap-then-promote strategy), the eval harness initially only reports **validator-pass rate**. Diff-against-golden is added incrementally as the corpus grows from promoted generations. A "structural similarity" check (same archetype × breakpoint produces broadly similar slot counts / placement) can land before full golden coverage as a coarser regression net.

**Used for**: iterating the skill — every time the SKILL.md changes, run the eval; merge only if validator-pass rate doesn't regress and (once goldens exist) golden-diffs don't regress.

**Where**: depends on Octo's testing surface. Either `scripts/eval-hierarchical-skill.mjs` here or in the Octo repo.
**Effort**: 1–2 days for the validator-only version; +1 day to add structural-similarity check; +0.5 day to add golden-diff once the corpus exists.

### 5. Octo integration

The harness that takes user prompts (from editors), invokes the Claude agent with this skill loaded, captures the `Page` artifact, runs the validator, and writes the artifact into the review queue.

**Owned by**: Octo (`Downloads/genuin/octo-canvas`). Confirmed from inspecting the octo-canvas codebase:

- **Agent runtime**: Octo uses `claude-agent-sdk` (Python) — the official Anthropic SDK that wraps the Claude Code CLI. The runner spawns `ClaudeAgentOptions(system_prompt={"type": "preset", "preset": "claude_code"}, cwd=<sandbox>, ...)` per session.
- **Skill discovery**: the Claude Code preset reads skills from the standard Anthropic locations inside the sandbox — `<cwd>/.claude/skills/<name>/SKILL.md` (project-level, preferred) and `~/.claude/skills/<name>/SKILL.md` (user-level). **No special skill format is required** — Markdown with YAML frontmatter (the convention already used for the existing `.team/skills/*` skills in this repo) works directly.
- **Figma MCP is available** to the agent at generation time. The agent can call `mcp__figma__get_design_context` / `mcp__figma__get_metadata` etc. directly against the file keys / node IDs listed in spec §6, with no extra plumbing in the SKILL.md beyond instructing the agent when to reach for it.
- **Allowed tools**: octo intentionally does not pin `allowed_tools`, so the agent has the full native Claude Code toolset plus Octo's `mcp__ui__ask_user` and the Figma MCP. New SDK tools appear automatically.

Remaining minor questions, none blocking:

- **Sandbox seeding**: does octo clone `genuin-webapp` (or a subset) into the sandbox cwd so `.claude/skills/hierarchical-tree/SKILL.md` arrives via `scripts/sync-ai-config.mjs`, or does octo extract just the SKILL.md and write it to `~/.claude/skills/`? Either works; one-message confirmation with the octo team will lock the delivery path.
- **Retry / failure handling**: agent retries internally (recommended: 2×) vs Octo retries the agent call. The plan recommends the split in Q6.
- **Page artifact persistence**: where octo writes the captured Page artifact (separate repo per spec, or staged into this repo for review). Determines whether the CI validator gate lives here or in octo.

## Recommended approach

Build v0 in four ordered chunks (reordered for the bootstrap-then-promote strategy — no upfront goldens to author, so the schema+validator and the SKILL.md can ship in parallel). Ship one PR per chunk so review and Octo integration can happen alongside.

1. **Validator + rule-checks + promotion pipeline** (chunk A, ~1 day; schema is built in walker plan chunk 1, not here). Skill chunk A authors `packages/hierarchical-tree/src/validate-rules.ts` (rule-check helpers), `scripts/validate-page-artifact.mjs` (CLI wrapper that imports `pageSchema` + rule helpers from `@genuin/hierarchical-tree`), and `scripts/promote-page-artifact.mjs` plus the empty `apps/webapp/src/content/page-artifacts/golden/` directory. No goldens authored — just the pipeline. **Cross-plan dependency**: skill chunk A starts after walker chunk 1 lands the Zod schema; until then, validator wiring is blocked.
2. **SKILL.md v0 + sync** (chunk B, ~1 day). Authors `.team/skills/hierarchical-tree/SKILL.md` with the full content from "What the skill must contain". Worked examples are seeded from (a) spec §2.4's tree sketch and (b) one small synthetic mobile artifact (~10 lines) inlined in the SKILL.md. References spec §6 Figma frames as the authoritative visual targets and instructs the agent to use Figma MCP when archetype shape is unclear. Runs `sync-ai-config.mjs` to propagate to `.claude/`.
3. **Smoke test with Octo + iteration + promotion** (chunk C, ~3–7 days, dominated by review-loop wall-time). The agent generates Page artifacts for the five archetype prompts × at least mobile + desktop. Outputs go through validator (machine gate) and editorial / design review against the Figma frames (human gate). Approved artifacts run through `scripts/promote-page-artifact.mjs` into the goldens directory. Expect to rewrite ~30% of the SKILL.md based on what fails. The human-review window is the spec §1 "review process before users see them" requirement in practice.
4. **Eval harness + CI** (chunk D, ~1.5 days). Loads skill, sends the canonical prompts, validates each output. v0 reports validator-pass rate only; structural-similarity check lands here too. Golden-diff added in v1 once the corpus is non-empty. CI gate wires the validator into commit checks on `Page` artifact paths.

The validator + SKILL.md are equally high-leverage and can run in parallel after the agreed locked decisions — pick whoever's hands are free for chunk A vs chunk B. Chunk C is the hard schedule dependency on the human-review window; nothing else blocks until then.

Octo readiness is the only external blocker for chunk C. If Octo's harness isn't ready, chunks A and B can still ship; chunk C waits.
